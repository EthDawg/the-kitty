## Findings

1. **Every run kept the Sheet intact.** None of the nine changed a cell in the measured ranges. Entries row counts held (1 and 1,083), no tab was renamed or moved, and the new tabs all went at the end with exact headers. Every row-2 formula is present with no errors, every list and checkbox has the note's values, and every new check reads OK. The original checks and the "Checks needing review" total are intact and still count (0 on H1, 6 on H2 and H3).
2. **All three models handled the collision.** On H3 every run left out Receipts, Receipt Lines and the three receipt checks. Every run left the household's Receipts tab unchanged (5 columns, 5 rows), pointed Goal Levers at 'Our goals', and asked the household about its receipts. H3-sonnet also recorded the 'Our goals' mapping on Decisions (D0020, confirmed on the Sheet).
3. **One real defect.** H1-haiku and H2-haiku wrote Goal Levers H2 (Date if off) without taking this lever out of the other-levers sums. For any lever that is on, Date if off then equals Date if on and Months moved reads 0. Empty tabs hide this. H3-haiku wrote it correctly.
4. **Models made different judgment calls.** Opus wrote the new checks below the total, so nothing moved. Haiku and Sonnet inserted rows above it, and Sheets rewrote Metrics!C20 from C25 to C31 (C26 to C29 on H3). The value is the same, but the formula text changed, which breaks the note's "every cell reads the same" rule (Metrics was outside the measured ranges). The two checks the note tags "(Note)" and "(Review)" got Type Data from Haiku and Cash from Opus. On H1 and H2, Sonnet put "Note" and "Review" in Type, which no existing row uses. On H3, Haiku kept sheet_version 2 until receipts are answered; Sonnet and Opus set 3. H2-haiku rewrote the note's N(+Receipts!J2:J). H2-opus tested the note's version and found it sums per row, so the rewrite was not needed.
5. **The note was unclear in places** (how many of the nine reports raised each point): Type or Status for "(Note)"/"(Review)", 8. No "Why it matters" / "Where to look" text, 7. N(+range) inside SUMPRODUCT, 6 (every run that wrote it). Where the new rows go, 5. Goal Levers hard-codes Goals!, 3 (all H3). Checkboxes fill FALSE, so the tabs look full to an append, 3 (all Opus; true on every Sheet). Which column takes the GST list, 2. "More than one pick" counts rows, not decisions, 2. Whether the version moves to 3 while receipts are held back, 2. "Receipt held" gets no step to read Receipts, 2. Raised once each: the H2 "lever left out" wording, the `<as-of>` placeholder, "past decide-by" counting only recommended rows, the README layer table, Months moved blank when a date is Never, and the risk that a version 3 page reads the household's own Receipts tab.
6. **Testing was thin.** Every new tab is empty, so these scores measure structure, not behaviour on real rows. Only H2-opus, H3-opus and H3-sonnet tried the formulas with temporary rows, and they removed those rows afterwards.
7. **Cost.** Haiku and Sonnet took 2.6 to 4.0 minutes and 129k to 186k tokens. Opus took 10.3 to 11.3 minutes and 215k to 262k tokens: about 3.9 times Sonnet's time and 1.7 times its tokens, for the same table score. The extra bought the no-move placement, the probes and the most precise list of gaps in the note. Sonnet used the fewest tokens on average (140k, against 165k for Haiku and 245k for Opus). H2-haiku's 50 tool uses include four failed calls it reported. Tokens are counts, not dollars.
